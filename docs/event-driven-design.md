# 경매 권리 분석 서비스 이벤트 설계

> 설계 단계의 메시지 계약이다. 애플리케이션 코드·브로커 설정은 아직 구현하지 않았다.

## 1. 적용 방식

세 프로세스를 유지하고, 처리 순서는 영구 작업 상태로 관리하며, 완료된 사실을 이벤트로 전달한다.

- 명령은 특정 책임자에게 작업을 요청한다.
- 이벤트는 이미 저장된 사실을 알리고 각 구독자는 자신의 처리를 수행한다.
- 작업 흐름 관리 모듈은 수집·파싱 워커 내부에 둔다. 별도 조정 서비스는 만들지 않는다.
- DB를 업무 상태의 기준으로 사용한다. 모든 상태를 이벤트 재생으로 복원하는 이벤트 소싱은 범위에 포함하지 않는다.
- HTTP 조회와 일반 관측성 수집은 기존 방식을 유지한다.
- 브로커 제품, 프로그래밍 언어, 스키마 검증 라이브러리는 구현 전에 선정한다.

## 2. 메시지 목록

### 명령

| 이름                        | 생산자       | 처리자                | 내용                          |
| ------------------------- | --------- | ------------------ | --------------------------- |
| `CollectCaseDocuments`    | 접수·조회 API | 수집·파싱 워커           | 지정한 사건·물건의 문서를 해당 입력 버전에 수집 |
| `FinalizeInputCollection` | 접수·조회 API | 수집·파싱 워커의 흐름 관리 모듈 | 업로드 목록 확정 후 분석 준비 조건 재평가    |

API는 업로드 목록 확정 상태와 `FinalizeInputCollection`을 같은 트랜잭션에 기록한다. 명령이 먼저 도착해도 문서 처리가 끝나지 않았다면 기다린다. 이후 파싱 완료 시 준비 조건을 다시 평가한다.

자동 수집은 워커가 수집 시도 종료와 누락 정보를 기록한 뒤 준비 조건을 평가한다. 업로드 전용 입력에 자동 수집 완료를 요구하지 않고, 혼합 입력에는 수집 종료와 사용자 입력 확정을 모두 요구한다.

### 이벤트

| 이름 | 발행하는 사실과 시점 | 생산자 | 초기 구독자 |
|---|---|---|---|
| `DocumentStored` | 저장된 원문을 확인하고 문서 버전을 특정 입력에 등록한 트랜잭션 완료 | 업로드 API 또는 수집·파싱 워커 | 문서 처리 |
| `AnalysisInputReady` | 입력 준비 조건 검증, 불변 스냅샷과 분석 작업 생성 트랜잭션 완료 | 수집·파싱 워커의 흐름 관리 모듈 | 분석 실행 |
| `ReportPublished` | 리포트 파일 저장 확인, 리포트 버전과 완료 상태 저장 트랜잭션 완료 | 분석·리포트 워커 | 리포트 목록 |

`DocumentStored`는 임시 파일 업로드 완료만을 뜻하지 않는다. 원문을 읽을 수 있고 사건·입력과의 등록 정보가 DB에 저장되어야 한다. 대상이 아직 불명확하면 후속 검증에서 확인 필요 상태로 둔다.

보완 입력에서 기존 원문을 재사용할 수 있다. 새 입력에 문서 버전이 등록되면 별도 `DocumentStored`를 생성하고, 검증된 파싱 결과는 원문·파서 버전이 같은 경우에만 재사용한다.

`AnalysisInputReady`는 분석을 완료했다는 뜻이 아니다. 외부 분석 호출을 시작할 수 있는 검증된 입력이 준비되었다는 사실이다.

`ReportPublished`의 발행은 파일과 완료 상태 저장 이후다. 공개 인터넷 접근 허용을 뜻하지 않으며, 리포트 조회 시 사용자 접근 권한을 검사한다.

`AnalysisCompleted`와 별도 리포트 생성 서비스는 초기 범위에서 제외한다. 분석·리포트 생성은 같은 워커가 담당한다. 새 자료 감지는 현재의 새 입력 버전 생성 흐름으로 처리하며 `AnalysisInputChanged`는 필요할 때 추가한다.

## 3. 구독과 처리 책임

| 논리 큐·구독 | 수신 메시지 | 실행 프로세스 | 중복 방지 기준 |
|---|---|---|---|
| 수집·흐름 관리 명령 큐 | 두 명령 | 수집·파싱 워커 | 명령 식별자 + 작업·입력 버전·명령 종류 |
| 문서 처리 구독 | `DocumentStored` | 수집·파싱 워커 | 구독자·이벤트 식별자 + 입력·문서·파서 버전 |
| 분석 실행 구독 | `AnalysisInputReady` | 분석·리포트 워커 | 구독자·이벤트 식별자 + 분석 작업 식별자 |
| 리포트 목록 구독 | `ReportPublished` | 접수·조회 API의 백그라운드 소비자 | 구독자·이벤트 식별자 + 리포트 식별자·버전 |

같은 구독의 워커 복제본은 메시지를 분담한다. 서로 다른 기능이 같은 이벤트를 모두 받아야 하면 기능별 내구성 있는 구독을 만든다. 같은 큐에서 알림과 목록 갱신이 경쟁하도록 구성하지 않는다.

향후 이메일 알림과 통계 집계는 별도 구독으로 추가한다. 알림 장애가 분석 실행 구독이나 리포트 목록 구독의 처리를 막지 않도록 실패·재시도 대상을 구독별로 분리한다.

API 안의 리포트 목록 소비자는 HTTP 요청 스레드와 별도의 제한된 실행 자원을 사용한다. 목록 이벤트 적체가 접수·조회 요청 자원을 모두 차지하지 않게 한다.

## 4. 입력 준비 조건과 버전

입력 버전마다 다음 값을 영구 저장한다.

- 입력 방식과 수집 정책
- 등록된 문서 버전 목록과 문서별 처리 상태
- 자동 수집의 종료 여부와 누락 자료
- 사용자 업로드 묶음의 확정 여부
- 자료 충족·대상 일치·상충 검증 결과
- 준비 이벤트 생성 여부, 입력 스냅샷 식별자, 분석 작업 식별자

분석 시작 조건은 다음과 같다.

1. 해당 입력 방식에서 요구하는 수집 종료·업로드 확정 조건을 만족한다.
2. 등록된 문서의 처리가 모두 끝났다.
3. 필수 자료와 대상 일치 여부를 확인했고, 차단해야 할 충돌이 없다.
4. 같은 작업·입력 버전에 대해 분석 준비 전환이 아직 수행되지 않았다.

수집 종료, 입력 확정, 문서 파싱 결과 저장 시 같은 판단 함수를 실행한다. 마지막 문서 처리와 입력 확정이 동시에 일어나도 놓치지 않도록 입력 버전 행 잠금 또는 동등한 동시성 제어를 사용한다.

스냅샷·분석 작업·준비 상태·Outbox 이벤트를 같은 트랜잭션에 저장한다. `job_id + input_version`에 대한 고유 제약으로 준비 전환의 중복을 막는다. 브로커 재전달로 이벤트가 여러 번 도착하는 것은 별도로 허용하고 처리한다.

업로드 확정 요청은 업로드 세션의 예정 파일 목록과 저장 완료 여부를 검증한다. 진행 중인 업로드가 있으면 확정을 보류하며, 늦게 도착한 파일을 조용히 누락시키지 않는다. 업로드 확정은 사용자 경로만 닫는다. 혼합 입력의 자동 수집 경로는 수집 종료까지 문서를 추가할 수 있다.

분석 준비 전환에서 전체 입력 스냅샷을 봉인한 뒤에는 문서 목록을 변경하지 않는다. 사용자의 새 자료·수정·의도적인 새 분석은 새 입력 버전으로 만들고, 이전 문서를 명시적으로 참조할 수 있게 한다. 실패한 실행의 재시도는 같은 분석 작업 식별자를 유지한다.

입력 버전은 작업 안에서 증가한다. 늦게 완료된 이전 버전 리포트는 이력에 보존하되, 최신 완료 리포트 포인터를 이전 버전으로 되돌리지 않는다. 최신 요청 버전이 진행 중이면 이전 리포트를 최신 입력의 결과처럼 표시하지 않는다.

## 5. 공통 메시지 계약

아래는 애플리케이션 자체 계약의 초안이다. 특정 표준과의 호환성을 선언하는 형식은 아니다.

| 필드 | 의미 |
|---|---|
| `message_id` | 메시지 고유 식별자. 같은 메시지의 재발행·재전달에서는 유지 |
| `message_kind` | 명령 또는 이벤트 구분 |
| `message_type` | 명령·이벤트 이름 |
| `schema_version` | 메시지 계약 버전 |
| `occurred_at` | 명령 기록 또는 사실 발생 시각 |
| `producer` | 메시지를 기록한 서비스 |
| `job_id` | 전체 사용자 작업 식별자 |
| `input_version` | 작업 안의 입력 버전 |
| `correlation_id` | 관련 처리 흐름을 연결하는 식별자 |
| `causation_id` | 직접 원인이 된 메시지 식별자. 사용자 최초 요청이면 생략 가능 |
| `traceparent` | 지원되는 추적 문맥. 장기 보존 작업 식별자를 대신하지 않음 |
| `data` | 이벤트별 불변 식별자·버전·참조 정보 |

`message_kind`의 직렬화 값은 `command` 또는 `event`로 한다. 시각은 시간대가 포함된 형식으로 기록한다.

이벤트별 최소 내용은 다음과 같다.

| 이벤트 | `data` 필수 내용 |
|---|---|
| `DocumentStored` | 입력 문서 등록 식별자, 문서 식별자·버전, 원문 해시, 출처 구분, 파서 버전 |
| `AnalysisInputReady` | 입력 스냅샷 식별자, 분석 작업 식별자 |
| `ReportPublished` | 분석 작업 식별자, 리포트 식별자·버전 |

최초 모델·프롬프트·규칙 버전은 분석 작업 생성 시 저장한다. 재시도할 때 배포된 최신 설정을 암묵적으로 적용하지 않는다.

다음은 합성 예시다.

```json
{
  "message_id": "5a1dd6a7-4b3c-43d8-bd64-bc51fb3e0cf1",
  "message_kind": "event",
  "message_type": "AnalysisInputReady",
  "schema_version": 1,
  "occurred_at": "2026-09-05T12:00:00+09:00",
  "producer": "ingest-worker",
  "job_id": "job-example-001",
  "input_version": 2,
  "correlation_id": "job-example-001",
  "causation_id": "cf88e37c-0487-4359-aa98-1db6b8b55eaf",
  "data": {
    "input_snapshot_id": "snapshot-example-002",
    "analysis_id": "analysis-example-002"
  }
}
```

문서 본문이나 임시 서명 URL을 메시지에 싣지 않는다. 소비자는 식별자로 불변 버전의 자료를 조회한다. 알 수 없는 계약 버전은 실패 기록으로 격리하고, 기존 필드의 의미를 바꾸는 변경은 새 계약 버전으로 도입한다.

## 6. 발행·소비와 복구

### 발행 대기함

업무 상태와 Outbox를 같은 DB 트랜잭션으로 저장한다. 내부 발행기는 큐의 수신 확인 뒤 발행 상태를 기록한다. 확인 직후 종료되면 같은 메시지가 다시 발행될 수 있으므로 `message_id`를 유지한다.

여러 복제본의 발행기는 행 선점 또는 임대를 사용한다. 미발행 이벤트 수와 가장 오래된 이벤트의 대기 시간을 수집하고, 재시도로도 진전이 없으면 알린다.

### 소비 기록

Inbox의 고유 기준은 `subscriber + message_id`다. 단순 수신 기록과 업무 처리 완료를 구분한다.

- 짧은 DB 처리에서는 업무 변경·후속 Outbox·Inbox 완료를 한 트랜잭션에 기록한 뒤 메시지를 확인한다.
- 파싱·AI 호출처럼 긴 작업은 먼저 임대와 실행 식별자로 선점하고 트랜잭션을 종료한다. 처리 결과와 완료 상태는 유효한 선점 소유자만 저장한다.
- 메시지 확인 전에 종료되면 재전달된 작업이 저장 상태를 확인한다. 임대 만료 후 재개할 수 있어야 한다.
- 같은 업무가 서로 다른 메시지로 전달될 수 있으므로 이벤트 식별자 중복 제거 외에 업무 고유 제약도 적용한다.
- 외부 AI 호출의 중복 비용은 Inbox만으로 막을 수 없다. 제공자 멱등성 지원, 호출 시도 이력, 타임아웃, 비용 상한을 별도로 적용한다.

### 재시도와 재생

일시 오류만 횟수·기한 내에서 백오프와 임의 지연으로 재시도한다. 반복 실패는 구독별 실패 큐 또는 동등한 영구 실패 기록에 격리한다. 운영자가 같은 작업을 재처리하면 기존 식별자와 입력 버전을 유지한다.

리포트 목록 조회 모델 재구축은 `ReportPublished`를 목록 구독에만 재전달하거나 저장된 리포트에서 복원한다. 전체 이벤트를 모든 구독에 무조건 재생해 AI 분석을 다시 호출하지 않는다. 브로커의 이력 보존 기간과 조회 모델 복구 방법은 제품 선정 시 함께 정한다.

## 7. 검증 시나리오

| 상황 | 기대 결과 |
|---|---|
| 문서 세 개 중 하나만 파싱 완료 | 분석이 시작되지 않음 |
| 업로드 확정이 문서 이벤트보다 먼저 도착 | 문서 처리 후 정상적으로 준비 상태에 도달 |
| 마지막 문서 처리와 입력 확정이 동시에 실행 | 입력 스냅샷·분석 작업이 한 번만 생성됨 |
| 같은 DocumentStored가 두 번 전달 | 해당 입력 문서 처리가 중복 완료되지 않음 |
| 다른 메시지 식별자로 같은 준비 사실 전달 | 같은 분석 작업에 대한 AI 실행을 중복 시작하지 않음 |
| DB 커밋 직후 브로커 발행 전 종료 | 재시작한 발행기가 Outbox를 전달 |
| 결과 저장 직후 메시지 확인 전 종료 | 재전달 시 결과를 재생성하지 않음 |
| AI 처리 후 응답 유실 | 설정된 정책으로 제한 재시도·비용 기록, 무제한 호출 없음 |
| 입력 버전 3 이후 버전 2 리포트 이벤트 도착 | 버전 2 이력 보존, 최신 포인터 유지 |
| 리포트 목록 구독 중단 | 원본 리포트 상세 조회 가능, 목록 지연 감지 |
| 목록 재구축 | 목록 구독만 처리하고 AI 재호출 없음 |
| 자료 수집 제공처 장애 | 업로드 경로 유지, 필수 자료 누락은 보완 필요로 표시 |
